Ada sedikit miskonsepsi yang perlu diluruskan, ini penting biar model mental lu bener.

Soal &rbuf[4] — ini bukan soal "gak nyentuh variable"

&rbuf[4] itu artinya "alamat memory di index ke-4 dari array rbuf". Operator & di sini fungsinya "ambil alamat", sama persis kayak konsep pointer di C yang udah lu kenal:

cpp
int x = 5;
int* p = &x;  // p = alamat memory tempat x disimpan
cpp
char rbuf[100];
char* ptr = &rbuf[4];  // ptr = alamat memory di posisi index 4 dari rbuf

Jadi &rbuf[4] itu ngasih pointer yang nunjuk ke tengah-tengah array, bukan ke awal array (rbuf doang = &rbuf[0]).

Soal std::string(&rbuf[4], len) — ini constructor, BUKAN string_view

Ini bagian yang perlu diluruskan: yang gw suruh pake itu std::string, bukan std::string_view. Beda penting:

  • std::string(ptr, len) → constructor yang bikin std::string BARU dengan COPY data sebanyak len byte mulai dari alamat ptr. Ini beneran nyalin datanya ke memory baru.
  • std::string_view(ptr, len) → ini yang "melihat tanpa menyentuh/copy" — cuma nyimpen pointer + panjang, gak ada data yang di-copy. Lebih ringan, tapi berbahaya kalau data aslinya berubah/hilang sementara string_view masih dipake (jadi "dangling").

Untuk kasus print doang (std::cout << ...), dua-duanya sebenernya bisa dipake dan sama-sama valid. Gw kasih contoh pake std::string karena lebih aman buat pemula (gak perlu mikirin lifetime issues).

Kenapa pake (ptr, len), bukan &rbuf[4] doang buat print

Ini jawaban dari pertanyaan gw kemarin. Coba inget: rbuf itu buffer besar (4 + k_max_msg = 4100 byte), tapi request yang beneran cuma sepanjang len byte (misal cuma 5 byte: "hello"). Sisa buffer (byte ke-9 sampai ke-4099) itu isinya garbage/data lama dari request sebelumnya (karena buffer di-reuse tiap kali work_req dipanggil).

Kalau lu print pake std::cout << &rbuf[4] doang (tanpa spesifikasi panjang), C++ bakal nge-treat &rbuf[4] itu sebagai C-style string — yang artinya dia bakal terus baca byte demi byte sampai ketemu null terminator (\0). Masalahnya: kalau data yang lu terima kebetulan gak ada \0 di posisi yang tepat (atau ada garbage sebelum ketemu \0), lu bisa print sampah/data sisa dari request sebelumnya, bukan cuma isi request yang sekarang.

Dengan std::string(&rbuf[4], len), lu secara eksplisit bilang "cuma ambil persis len byte dari sini, JANGAN peduli null terminator". Ini lebih aman dan predictable — sesuai sama filosofi length-prefixed protocol yang emang tujuannya biar lu SELALU tau persis berapa byte yang valid, gak perlu nebak-nebak dari null terminator.

static int32_t read_full(int fd, char *buf, size_t n){
    while(n > 0){
        ssize_t rv = read(fd, buf, n);
        if(rv <= 0) return -1; //err
        assert((size_t)rv <= n);
        n -= (size_t)rv;
        buf += rv;
    }
    return 0;
}

        n-=(size_t)rv;
        buf+= rv;
    }
    return 0;
}

Thought for 4s

Ini bug bukan di kode work_req lu — logic-nya udah bener. Masalahnya ada di cara testing: lu kemungkinan connect pake nc terus ngetik text biasa, kayak sebelumnya. Tapi sekarang server udah expect binary protocol (4-byte length prefix duluan), bukan text mentah.

Kenapa ini kejadian

Waktu lu ngetik teks di nc (misal hello), itu dikirim sebagai raw text h-e-l-l-o-\n. Server sekarang baca 4 byte pertama dari itu dan nge-interpretasi-in sebagai angka uint32_t (little-endian) — padahal itu bukan angka, itu karakter ASCII dari kata hello. Kalau di-convert jadi angka, hasilnya bisa jadi angka raksasa (jutaan/miliaran), jauh di atas k_max_msg (4096), makanya langsung kena validasi len > k_max_msg dan abort().

Ini sebenernya sinyal validasi lu JALAN dengan benar — server nolak input yang gak sesuai protokol. Masalahnya cuma nc bukan tool yang tepat buat testing protokol binary kayak gini.

Solusinya: bikin client sendiri

Ini juga bagian dari chapter 04 (section 4.3) — kita perlu bikin program client terpisah yang ngirim data dengan format protokol yang sama (length-prefixed), biar bisa testing end-to-end dengan bener.
